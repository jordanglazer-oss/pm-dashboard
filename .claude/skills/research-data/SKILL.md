# Research, theses, themes and ingested analyst data

> Before writing any key below, run the Redis-safety checklist in CLAUDE.md (keys touched, read-modify-write, concurrent writers, rollback, admin-route `?confirm=YES` + stash + diff, recent Blob backup). Everything here was moved verbatim from CLAUDE.md; nothing was summarised away.

## Per-key detail (moved from CLAUDE.md)

- **`pm:stocks-suggested`** — Stock-shaped **staging records** for the Suggested funnel (`app/lib/suggested-stocks.ts`), one per name on 2+ bullish research lists that the book doesn't already track. Exists because the provider exports (SIA / MarketEdge / BoostedAI) now cover suggested names too, and a name with no `Stock` record has nowhere for that data to land — every row was parsed and dropped. Same shape as a book stock plus `suggestedSince` / `fallenOffAt`. **Why a separate key and not a third bucket inside `pm:stocks`:** ~113 call sites across 47 files treat `bucket` as binary in ways TypeScript cannot flag, so a "Suggested" entry in the book blob would silently reach the brief, alert digests, change monitor, PIM eligibility and the risk lens. With its own key every existing `pm:stocks` reader is unchanged by construction. Reconciled by `POST /api/suggested-watchlist` (creates records for qualifying names, drops ones the book now tracks, prunes a fallen-off record ONLY when it is empty — nothing scored, no provider data, no notes — and keeps + marks anything carrying data; stashes the pre-image at `pm:stocks-suggested.pre-sync-<ts>` before any drop). Written by the email ingest + manual Inbox importers (`applyPatchesToRedis` routes each patch to the store holding the ticker, **book first**) and by on-demand scoring from the Suggested tab. `POST /api/kv/stocks-suggested` merges ONE record at a time — **there is deliberately no whole-array PUT**, so a stale client can't roll back a sync or an ingest. Scoring reads it via `readStockPool()` (`app/lib/stock-pool.ts`). Promotion copies the record into `pm:stocks` with its scores + provider data. Backed up (not excluded). Losing it costs the staged data for un-promoted names; the next refresh recreates empty records.
- **`pm:attachments`** (manifest, Redis) + **Blob `attachments/<id>`** (files) — screenshot AND PDF storage for the Brief (Equity Flows / Newton) and Research (Upticks / Fundstrat / RBC / Alpha Picks). Split intentionally: `pm:attachments` holds only a lightweight manifest array (`id`, `label`, `section`, `addedAt` — no dataUrl); each file's dataUrl now lives in **Vercel Blob** at `attachments/<id>` (it used to be a `pm:attachment:<id>` Redis key — that was an OOM source; a legacy Redis fallback remains for un-migrated reads). The dataUrl can be `data:image/...;base64,...` (image, max 10MB raw — re-compressed to JPEG client-side) OR `data:application/pdf;base64,...` (PDF, max 15MB raw, pass-through with no re-encoding). Backend block builders in upticks-scrape, research-scrape, and morning-brief detect the MIME prefix and emit either an Anthropic `image` block or a `document` block (PDF). The hash-gated cache pattern works identically for both — same dataUrl → same hash → cache hit. Split storage is load-bearing: a single blob holding 11 JPM screenshots would exceed per-value write limits and silently drop on save, making attachments vanish across refreshes. Managed by `/api/kv/attachments` (manifest GET/PUT) and `/api/kv/attachments/[id]` (file GET/PUT/DELETE). The GET manifest route includes a one-shot lazy migration that splits any legacy inline-dataUrl entries. Safe to delete individual `pm:attachment:<id>` keys; the manifest will filter out missing ids on next hydration. When refactoring, NEVER reintroduce dataUrls into the manifest blob or into `pm:research.attachments` — research's `save` helper strips them before each PUT for the same reason.
- **`pm:street-takeaways`** — per-ticker log of parsed FactSet alert emails (`{ [TICKER]: StreetTakeaway[] }`, newest first). FOUR `kind`s share the store, each with its OWN retention window so they never evict one another: `takeaways` (Street Takeaways — the per-firm analyst roundup: PT changes with valuation basis + distilled argument, full-panel rating mix, average target, valuation vs the name's own 5-year history, consensus estimate revisions), `metrics` (StreetAccount Metrics Recap — reported results vs consensus, guidance vs prior guide, beat track record), `transcript` (Transcript Intelligence), and `news` (Top News Summaries flashes + manual forwards — a development BETWEEN prints: headline, the facts behind it, and every stated figure with its baseline). Earnings kinds keep `MAX_PER_KIND` (8) for `MAX_AGE_DAYS` (365); news keeps `MAX_NEWS_PER_TICKER` (10) for `NEWS_MAX_AGE_DAYS` (180) — news arrives on no schedule and goes stale faster. Ingested via the Gmail inbox — these are BODY-TEXT emails (no attachment), matched by sender (`FactSet_Alerts@factset.com`), by subject (`SA: …`, `Street Takeaways`, or the manual `News: <TICKER> …` / `FYI:` / `Note:` convention with the ticker in CAPS), or by the alert's own body footer (`isFactsetAlertBody`); parsed by a small Anthropic call in `app/lib/street-takeaways-parse.ts` against one of three schemas chosen by `detectTakeawayKind`, and scoped to Portfolio/Watchlist names (others skipped BEFORE any Anthropic call, so an off-book forward costs nothing). Deduped on (ticker, date, kind, event) — an earnings-kind duplicate that is a "Revised:" alert or carries more content REPLACES the stored one — or (ticker, date, kind, normalized headline) for `news`, since several unrelated flashes can land on one day. Feeds the scoring prompt (catalysts / trackRecord / historicalValuation), `app/lib/thesis-evidence.ts` (2 earnings alerts + 2 news flashes), the synthesis screen, and the stock page's FactSet Alerts tile. Read-only w.r.t. `pm:stocks` — it NEVER writes a score. Losing it costs the ingested analyst context until the next alerts arrive.
- **`pm:earnings-previews`** — parsed FactSet "Consensus Metrics Preview" emails (`app/lib/earnings-previews.ts`): `{ [TICKER]: EarningsPreview[] }` (consensus lines with ranges, the company guide in effect, what to watch, implied move), newest first, ≤6 per ticker, 200 days. EXPECTATIONS, not results — deliberately NOT in `pm:street-takeaways`, whose readers treat every entry as something that happened (before this a preview was read against the results schema and filed as actuals). Written only by the email ingest (`handleStreetTakeaways` routes a preview here BEFORE the takeaway parser; read-merge-write of one ticker; a re-forward replaces). Book names only. Read by the earnings-comparison watcher. Losing it only means the next recap is judged against its own consensus figures.
- **`pm:position-theses` pillars (Phase 2, Nov 2026)** — each pillar may carry `measures` (reported lines read as a TREND across every FactSet Metrics Recap on file — `pillarTrends` in `app/lib/metric-resolver.ts`, served by `/api/thesis-signals`, zero tokens) and a PM-signed `status` (`intact` / `watch` / `broken`) + `statusNote`. `statusSince` is stamped SERVER-side in `POST /api/kv/position-theses` (changed status → today; unchanged → stored date). Draft with AI (`/api/thesis-draft`, main key, Sonnet + up to 6 web searches, ~15¢, writes nothing) now PROPOSES the whole long-term thesis: 3-5 pillars with `measures` (validated against recap labels on file) and a status + evidence note (`statusBy: "ai"`), 1-3 custom breakers, at most one metric guard per pillar, and `themes` (`{ name, role, exposure? }`, stored on the entry, accepted by the POST route). It no longer proposes SIA / Equate / MarketEdge / revisions / technical conditions. A status is only stored when the PM saves (signs); changing it in the editor sets `statusBy: "pm"`. The AI review's confirmed/contested/broken stays a separate, per-review reading; since Phase 2 step 4 the review (`app/lib/thesis-review.ts`, main key, hash-gated, `pm:thesis-review:{TK}`) also sees each pillar's signed status + evidence trend + themes, may propose `status` changes (accepted in the tile like any other change, then signed), proposes only `metric` / `custom` conditions, and runs straight after a `metrics` recap or `news` item is ingested for that ticker (`after()` in inbox-dispatch, after the earnings comparison) as well as in the nightly sweep. All fields optional; old entries parse unchanged.
- **`pm:position-theses-archive`** — theses REMOVED from the Thesis desk (sold names): `{ [TICKER]: (PositionThesis & { removedAt })[] }`, newest last, ≤5 per ticker (`app/lib/thesis-archive.ts`). Written ONLY by `DELETE /api/kv/position-theses?ticker=&confirm=YES` (archives the entry FIRST, then drops it from `pm:position-theses`) and `POST /api/kv/position-theses/archive` (restore — refuses 409 if the name already has a live thesis). **BACKED UP.** Losing it only loses the ability to undo a removal.
- **`pm:themes`** — the investment themes (Phase 2, `app/lib/themes.ts`): `{ themes: { [id]: { id, name, aliases?, summary?, pillars: [{ id, title, claim, status?, statusNote?, statusSince?, statusBy? }], bellwethers: [{ ticker, name?, why }], aiDrafted?, signedAt?, updatedAt, archivedAt?, history? } } }`. Written ONLY by `POST /api/themes` (the PM signing ONE theme — read-merge-write of that id, prior version into `history` ≤ 8; `{ id, archive|restore }` toggles `archivedAt`, never a hard delete). `/api/themes/draft` (main key, Sonnet + up to 6 web searches, ~15¢) writes nothing. Membership is NOT stored: `buildThemeViews` matches each signed thesis's `themes[]` against a theme's name + aliases and computes the members' share of the PIM model's non-Core equity. **BACKED UP.** Page: `/themes`.
- **`pm:theme-evidence`** — FactSet alerts for theme BELLWETHERS that are not in the book: `{ [TICKER]: StreetTakeaway-shaped[] }`, ≤ 8 per ticker, 200 days. Written only by the email ingest (`handleStreetTakeaways`: a non-book identifier that matches a live theme's bellwether is parsed — main key, ~1¢ — and filed here; previews skipped). Deliberately NOT `pm:street-takeaways`, whose readers treat every key as a book name. Bellwether alerts only arrive once the PM adds those names to the FactSet alert list. **BACKED UP.**
- **`pm:research-synthesis`** — PERSISTED cross-source synthesis blob shown at the top of the Research page (`{ result, generatedAt, generatedDate, briefRegime?, briefDate? }`). Strict stickiness model: once generated, the synthesis is anchored to the brief that existed at generation time and DOES NOT regenerate on page reload, even if the brief is regenerated mid-day. Reads use `GET /api/research-synthesis` (zero Anthropic spend). The first-ever generation auto-fires when no blob is persisted; subsequent reloads always read the cached blob. The "Force re-generate" button is the ONLY path that overwrites the persisted blob — it uses the current brief at the moment of the click. Portfolio holdings (from `pm:stocks` where `bucket === "Portfolio"`) are excluded from `topPicks` and `honorableMentions` both via prompt instruction and a server-side filter pass. Safe to nuke (next page load auto-generates a new one).
